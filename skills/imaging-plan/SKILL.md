# 卫星成图编成

把一个"要覆盖多大面积、多清晰、多久能拿到"的需求，反推成一份星座编成方案。

## 什么时候用

- "覆盖 XX 90% 需要几颗星"
- "给定 3 颗星，能覆盖多少"
- "达到 24 小时重访需要几颗星"
- "给我排一个成图计划 / 出个方案"

## 什么时候不要用

| 场景 | 去哪 |
| --- | --- |
| 只问"明天有哪些过境""哪次过境最合适" | `pass-planning` |
| 问 TLE 新不新鲜、同步失败 | `tle-health` |
| 问卫星参数、在轨位置 | `ephemeris-query` |
| 目标范围在浙江省以外 | 直接拒绝，本版本只支持浙江 |
| 问云量、天气、成像质量 | 本 skill 不涉及 |
| 同时要求"覆盖率 + 重访间隔"的组合目标 | 本版本没有组合模式：先问清主目标，只按一个模式出方案；需要两个指标就出两份 |

## 流程

> **提问规则：每次 `ask_user_question` 只放一个问题。** 拿到回答后再决定下一问，
> 不要一次把所有缺失字段列出来，也不要在问题里预告"后面还要问覆盖率"。
> 公共顺序固定：`mode → aoi → sensor_types → max_resolution_m`，
> 之后**只问当前模式需要的字段**（见下表）。

| 模式 | 模式专属字段（按顺序问） | 这个模式**不要问** |
| --- | --- | --- |
| `min_sats_for_coverage` 最少星达覆盖率 | `target_coverage_pct` | `n_sats`、`target_max_gap_hours` |
| `min_sats_for_revisit` 最少星达重访 | `target_max_gap_hours` | `n_sats`、`target_coverage_pct` |
| `max_coverage_for_n` 给定 N 颗最大覆盖 | `n_sats` → `hours`（时间窗） | `target_coverage_pct` |
| `min_wait_for_n` 给定 N 颗最小等待 | `n_sats` → `hours`（时间窗） | `target_coverage_pct` |

> **为什么给定 N 颗不问覆盖率**：这个模式里覆盖率是**输出**，不是输入；决定答案的是
> **时间窗**——同样 3 颗星，24 小时和 14 天的覆盖率差很多。让用户先填一个覆盖率，
> 等于让他预设一个会被结果推翻的数字。

1. **确定任务模式**（必需）——四选一：
   `min_sats_for_coverage` 最少星达覆盖率 / `min_sats_for_revisit` 最少星达重访 /
   `max_coverage_for_n` 给定 N 颗最大覆盖（**在给定时间窗内**）/
   `min_wait_for_n` 给定 N 颗最小等待。
   用户已经说清目标（"3 颗能覆盖多少"）时直接采用，不要重复问；
   选项描述里也要写"在时间窗内"，避免用户以为覆盖率是输入。
2. **确定目标范围**（必需）——先调 `mcp__rs-service__list_aoi`（默认 `level=city`）取可选范围；
   提问时 `options` 只能来自返回的 `items`（当前为浙江 11 个地级市），另外允许用户自定义 adcode、名称或 `POLYGON` WKT。
   浙江省外（北京、上海等）**不得作为选项**；用户主动提出时直接拒绝并说明本版本只支持浙江。
3. **确定传感器类型**（必需）——`optical` / `sar` / `hyperspectral`，可多选。默认三类全开。
   微波星（HY-2 系列等）是非成像载荷，不在枚举里。
4. **确定最大分辨率**（必需，单位米）——问法是"不差于多少米"，数值越小越清晰。
   常见档位 1 / 5 / 10 / 30 米，也允许用户直接给数值。
5. **按模式问专属字段**（每次只问一个）：
   - `min_sats_for_coverage`：问目标覆盖率（1–100%）。
   - `min_sats_for_revisit`：问 P95 重访上限（小时）；覆盖率是输出，不问。
     上限要明显小于时间窗（例如 72h 窗口配 24h 上限），否则 1 颗星也能满足，没有意义。
   - `max_coverage_for_n`：先问星数 N（1–20 的整数），**再问时间窗 `hours`**
     （24 / 72 / 168 / 336 四档）；不问覆盖率。
   - `min_wait_for_n`：先问星数 N，再问时间窗 `hours`；不问覆盖率。
6. **时间窗口径**：给定 N 颗的模式必须按用户的时间窗算，**不自动扩窗**；
   其余模式默认 72 小时，用户没提就不单独问，但结论里要写明窗口。
   只有 `min_sats_for_coverage` 会在达不到目标时自动扩窗（72h→7d→14d）。
7. **求解，同一组参数只算一次**（参数与模式对应关系见 `COMMANDS.md`）：
   - 要出 HTML 报告（默认）：用 CLI 落盘——
     `~/桌面/RS-Service/.venv/bin/rs-service plan coverage … --out reports/<名称>.json`
     （CLI 不在 PATH 里，固定走这个 venv），stdout 里的 JSON 就是结论；
   - 只要结论、不出报告：调 `mcp__rs-service__plan_coverage`。
   - 两者共用同一 service 层、结果一致；**不要先 MCP 再 CLI 重算**——会跑两遍、
     写两条 `coverage_snapshot`，还可能因时间基准不同给出两个数。
8. **渲染报告**：`skills/imaging-plan/scripts/render.sh --in reports/<名称>.json --out reports/<名称>.html`
   （固定走项目 venv，含 jinja2），生成 HTML；给出 `reports/` 下的绝对路径，前端会把它变成可点击链接。
   报告含"卫星构成 / 覆盖与回放 / 推荐计划 / 口径与精度"四节；推荐计划里的数据来源是库中该星
   最近一次 TLE 的源（CelesTrak GP），右上角可切换深/浅主题。重访 P95/MRT 只在 API/JSON 里提供，报告不再展示。

## 参数不全怎么办

工具不会猜。它返回：

```json
{"ok": false, "error": "missing_params",
 "missing": ["max_resolution_m"],
 "schema": {"max_resolution_m": {"type": "number", "unit": "m", ...}}}
```

收到这个错误时：

- 只取 `missing` 里的**第一个**字段，用 `ask_user_question` 问**这一个**问题
  （`questions` 数组只放 1 项）；拿到回答后再重新检查 `missing`，问下一个；
- 不要一次列出全部缺失字段，也不要把多个问题塞进同一次调用；
- `options` 直接作为选项；`aoi` 的选项必须来自 `list_aoi` 的返回，
  不要凭常识补充省外城市；
- 没有 `ask_user_question` 时用文本追问，同样一次只问一个；
- 用户已经给过的字段直接跳过，不要重复问。

无论哪种，都**不要替用户假设默认值**（除了 `sensor_types` 默认三类全开、`hours` 默认 72）。

## 用户没回答 / 提问超时怎么办

`ask_user_question` 返回 `user did not answer the question`、或 SSE 断线导致问题丢失时：

- **不要立刻把同一个问题原样再问一遍**：断线不等于用户跳过，连续重问会把流程卡死；
- 先把已经拿到的参数和"还差哪一个字段"写清楚，停下来等用户回复；
- 用户回复后，从缺的那个字段继续，不要从头再问一遍；
- 如果连续两轮都拿不到回答，直接说明缺哪个参数、无法出方案，不要猜默认值。

## 输出口径（必须随结果一起说）

- 覆盖率、重访间隔都是**估算值**，带 `estimate` 含义；不得说"精确覆盖""保证重访"。
- 光学/高光谱只统计**太阳高度 >10°** 且云量达标的访问；夜间过境不算覆盖，不要说"光学全天时"。
- 过境时间误差 ±1 分钟，足迹边缘 ±2–5 km。
- 重访间隔默认看 **P95**（保证性），平均值会被密集过境拉好看。
- **未覆盖**（窗口内从未被访问的格点，`plan.uncovered_point_count`）与**只访问一次**
  （`plan.under_covered_points`，重访按窗口长度计）是两个不同的数，不要混着说。
- **给定 N 颗的模式**：覆盖率只对报告里那个时间窗成立，必须连窗口一起说
  （例："3 颗星、72 小时内最大覆盖 78%"），不得说成"长期/任意时间覆盖"。
- **自动扩窗**只发生在 `min_sats_for_coverage`：如果 `window.extended_to_hours` 大于你给的
  `hours`，结论必须写实际窗口（如"扩到 14 天后覆盖 90%"），不能仍说"72 小时"。
- 报告里保留 `algo_version` / `parser_version`；网格间距保留在原始 JSON 中，便于复现（报告界面不展示）。

## 出方案前自检

- [ ] 当前模式用不到的字段没有问（尤其给定 N 颗时没问覆盖率）；
- [ ] 给定 N 颗时问了时间窗 `hours`，结论里带了这个窗口；
- [ ] 同一组参数只解了一次（MCP 与 CLI 二选一，不重算）；
- [ ] 报告标题与模式一致（"给定 N 颗…最大覆盖" / "覆盖 X% 需要 Y 颗" / "重访 P95 ≤ …"）；
- [ ] 未覆盖格点（`uncovered_point_count`）与只访问一次（`under_covered_points`）没有说混；
- [ ] 结论带 `estimate`、时间窗、P95 口径，没有"保证/精确"字样。
